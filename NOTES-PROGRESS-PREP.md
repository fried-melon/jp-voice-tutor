## Schema sketch (evidence model, draft)
- Session record: session_id, started_at, duration_s, lesson_id, end_state.
- Transcript record: session_id FK, seq, role (clerk/learner), text, ts. Full conversation TEXT retained privately per explicit user approval; no audio.

## Verified effect facts (fetched 2026-11-03, sources below)

### Workers KV free tier (developers.cloudflare.com/kv/platform/pricing/)
- 100,000 reads/day, 1,000 writes/day, 1,000 deletes/day, 1,000 list/day, 1 GB stored. Daily reset 00:00 UTC. Overage = hard operation errors, NOT billing. No egress charges. Dashboard/wrangler ops count toward usage.

### D1 free tier (developers.cloudflare.com/d1/platform/pricing/ + /d1/platform/limits/)
- 5M rows read/day, 100K rows written/day, daily reset 00:00 UTC, overage = hard errors not billing, no egress. Max database size 500 MB free, max account storage 5 GB free.

### Durable Objects free tier (developers.cloudflare.com/durable-objects/platform/pricing/)
- Free plan: SQLite-backed DO only. 100,000 requests/day, 13,000 GB-s/day duration (hibernating idle not billed), 5M rows read/day, 100K rows written/day, 5 GB SQL stored total. Daily reset 00:00 UTC, overage = hard errors. Deletes count as rows written. Duration bills 128MB allocation while active.

### Binding impact on existing worker jp-tutor-owner-token
- wrangler.jsonc already binds two DO classes (LIMITS=IssuanceLimit, REVIEW_PROJECTION=ReviewProjectionDO). Adding a KV namespace, D1 database, or a third DO class is a config addition to the same deployed worker - no new account, no new grant. Each new binding does create a new storage resource in the Cloudflare account: that IS the "new live storage" step requiring scoped review before any live write (parent 23:35 model).
- KV/D1/DO bindings are independent per class/namespace; a new binding does not touch LIMITS DO state or code.

### Delete/backup/export paths per option
- KV: delete via API/wrangler per key or whole namespace; export = list+read all keys (1,000 list/day free caps bulk export speed); backup = same read path to Drive.
- D1: delete rows or drop database via wrangler; export = `wrangler d1 export` (SQL dump); backup = dump to Drive.
- DO (SQLite): delete = delete class + objects; export = per-object storage read via RPC (no native dump); backup = app-level export endpoint.
- Sheets (existing Google access): user-visible file, delete in Drive, export native; BUT OAuth revoke is project-grant-wide = kills owner login (GrantDO review finding). GrantDO code currently excised from deploys pending user decision.
- Device-local IndexedDB: delete = app clear; export = app-generated file; loss on device change/browser clear; shared-device exposure. Complement only.

## Recommendation (for review, no live writes yet)
**Primary: one new D1 database bound to the existing worker.** Rationale: notes/progress is relational per-card evidence (joins across sessions/cards), D1's free tier is the roomiest (5M reads/100K writes per day vs KV's 1K writes/day which a per-card evidence writer could approach; DO adds request/duration metering KV/D1 lack), native SQL export for backups, hard-error overage means zero cost risk on the free plan.
- Schema: sessions(session_id PK, started_at, duration_s, lesson_id, end_state), card_evidence(session_id FK, card_id, heard_asr_phrases JSON, mo_ichido_count_by_role JSON, completed INT), mastery(card_id PK, first_independent_recall_session_id FK, confirmed_at). Completion != mastery enforced by separate tables.
- Access model: worker-only reads/writes behind the same owner gate pattern as live-token (gate stays closed; no new unauthenticated surface).
- Delete path: per-session delete endpoint + full wipe = drop table contents via wrangler; backup: scheduled `wrangler d1 export` to Drive (same 25MB-split convention).
- Volume sanity: a 5-min session yields ~dozens of card_evidence rows; 100K writes/day free = thousands of sessions/day headroom. 500MB/db = years of text rows.
**Complement: device-local IndexedDB cache** of the notes view for offline read, clearly labeled non-authoritative; never the sole store.
**Rejected for primary**: KV (1K writes/day too tight for per-card evidence, no relational queries), DO (request+duration metering unnecessary for a write-rarely/read-occasionally store, no native export), Sheets (revoke blast radius kills owner login; couples records to a personal Drive surface).
**Open before any live write**: parent scoped review of this recommendation; migration = none needed (greenfield); no test learner data.

## No-silent-loss design (added Nov 3 01:52, per main review)
- 4000-char bound is PER ENTRY (server validation, request hygiene), never a
  clip: capture spills overflow into same-role continuation entries; full
  session text preserved. Tested incl. streaming-chunk boundary crossing.
- Whole-session save failures never drop data: expired/401 -> ONE silent GIS
  auto_select refresh (fresh Google id token, zero taps when the browser has a
  consented Google session) + retry; transient (network/429/5xx) -> 2 backoff
  retries; still unsent -> bounded localStorage FIFO queue (3 sessions),
  flushed on next finish/load, plus a VISIBLE Korean notice on every failure.
- Cookie scope UNCHANGED: owner session cookie still excluded from learner
  data (docs/SESSION-COOKIE.md); notes stay Bearer-Google-token-only. The
  cookie-resume path (no id token in memory) saves via the silent refresh at
  session end; only if Google session is gone does the user see a notice, and
  the bundle waits on-device. No new sign-in in the common case.
- Whole-session retry idempotency: INSERT OR REPLACE by session_id server-side
  (tested); client queue dedupes by session_id (tested).

## Identity gating (added Nov 3 02:07, per main review)
- Stored sub is namespacing, not authentication. Queue read/flush/export/delete
  and the recovery bar run ONLY while owner-check has verified the current
  owner this page-load (cookie or Bearer). verifiedOwnerSub comes only from a
  server-verified Bearer; decode-only JWT subs are rejected (resolveScope).
- Signed-out or wrong-account: retained data stays on device but is fully
  hidden and untouched (bar removed, no flush). Logout/'키 삭제' never delete.
- Quota-full ('failed'): the CURRENT unsaved bundle is kept in memory and the
  recovery bar offers its direct export immediately (it was already on screen);
  sign-in guidance shown when unverified.
- Manual localhost mode (no token service) treats the device as verified
  ('local-dev' scope) - dev-only path, documented.
- Limitation: harness builds compile the token service out, so signed-out /
  wrong-account PAGE-LOAD behavior is unit-tested at the decision layer
  (resolveScope tests) but not browser-e2e; hosted verification pending D.
